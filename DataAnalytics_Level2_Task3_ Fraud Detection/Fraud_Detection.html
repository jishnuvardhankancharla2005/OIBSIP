Fraud Detection on Imbalanced Transaction Data¶

Objective: Build a machine learning pipeline that detects fraudulent credit card transactions, treating class imbalance as the central challenge rather than an afterthought.

Dataset: credit_card_fraud_10k.csv — 10,000 transactions with 8 features (amount, hour, merchant category, foreign-transaction flag, location-mismatch flag, device trust score, 24h transaction velocity, cardholder age) and a binary is_fraud label.

3. Why Standard Accuracy Is a Misleading Metric Here¶

Consider a trivial "model" that always predicts every transaction as legitimate, never flagging a single fraud case. Its accuracy would be:

In [8]:
baseline_accuracy = 1 - df['is_fraud'].mean()
print(f"Accuracy of a model that never predicts fraud: {baseline_accuracy:.4f} ({baseline_accuracy*100:.2f}%)")

Accuracy of a model that never predicts fraud: 0.9849 (98.49%)

This "do-nothing" model scores 98.49% accuracy while catching zero fraud — the single most important failure mode a fraud detection system exists to prevent. This happens precisely because accuracy weighs every correct prediction equally, and with a 65:1 class ratio, getting the majority class right on autopilot is nearly free.

This is why the rest of this notebook evaluates models using precision, recall, F1-score, and AUC-ROC instead of leading with accuracy — accuracy is reported alongside them for context, but never as the primary metric a model is judged on. A fraud detection system's entire value proposition is catching the rare positive class; a metric that can be gamed by ignoring that class entirely is not fit for purpose here.

4. Handling Class Imbalance: SMOTE¶

SMOTE (Synthetic Minority Oversampling Technique) generates new, synthetic fraud examples by interpolating between existing fraud cases and their nearest fraud neighbours in feature space — rather than simply duplicating existing minority rows (which would just make a model memorise the same 151 points harder), it creates plausible new points along the same regions of feature space where fraud already occurs.

Critical detail — SMOTE is applied to the training set only, after the train/test split, never before. Applying it before splitting would leak synthetic points derived from what should be unseen test fraud cases into the training set (via their nearest neighbours), inflating evaluation scores artificially. The test set is left in its original, real-world imbalanced state throughout, since that's what the model will actually face in deployment.

  • Logistic Regression — a fast, interpretable linear baseline; its coefficients directly show each feature's direction and strength of effect on fraud odds.
  • Random Forest — a non-linear ensemble that can capture interactions between features (e.g. "foreign AND low trust score AND high velocity" being far more suspicious than any single flag alone).

7. Evaluation: Precision, Recall, F1, and AUC-ROC¶

In [13]:
def evaluate(name, y_true, y_pred, y_proba):
    acc = accuracy_score(y_true, y_pred)
    prec = precision_score(y_true, y_pred)
    rec = recall_score(y_true, y_pred)
    f1 = f1_score(y_true, y_pred)
    auc = roc_auc_score(y_true, y_proba)
    print(f"=== {name} ===")
    print(f"Accuracy:  {acc:.4f}  (shown for context only, not for judging the model)")
    print(f"Precision: {prec:.4f}")
    print(f"Recall:    {rec:.4f}")
    print(f"F1-score:  {f1:.4f}")
    print(f"AUC-ROC:   {auc:.4f}")
    print()
    print(classification_report(y_true, y_pred, target_names=['Legitimate', 'Fraud'], zero_division=0))
    return {'Model': name, 'Accuracy': acc, 'Precision': prec, 'Recall': rec, 'F1': f1, 'AUC-ROC': auc}

Observation: the two models tell very different stories despite both being trained the same way.

  • Logistic Regression catches 93% of fraud (recall) but at the cost of very low precision (29%) — it flags roughly 3 legitimate transactions as fraud for every 1 real fraud case it correctly catches (69 false positives vs. 28 true positives).

8. Which Metric Matters Most for Fraud Detection?¶

The honest answer: it depends on the cost structure of the business, but recall is usually weighted more heavily than precision — up to a point.

  • A false negative (fraud that slips through undetected) means the cardholder or the bank absorbs a real financial loss, and the fraudulent pattern goes uncaught and can repeat.
  • A false positive (a legitimate transaction flagged as fraud) costs a customer-service review, a possibly-declined purchase, and some customer annoyance — real, but generally far cheaper than an actual fraud loss.

This asymmetry is why recall is usually the metric fraud teams protect first — missing fraud is the more expensive mistake. This is exactly why Logistic Regression's 93% recall is genuinely valuable despite its low precision: in a real deployment, its output would typically feed a secondary review queue (a human analyst or a stricter second-stage model) rather than auto-declining every flagged transaction, making the false-positive cost more tolerable than it looks in isolation.

That said, precision cannot be ignored entirely — at Logistic Regression's precision level (29%), a bank processing millions of transactions would flood its fraud review team with false alarms, burning out analysts and slowing down legitimate customers at scale. Random Forest's more balanced precision/recall trade-off (79% / 73%) is likely the more operationally realistic choice for a system that auto-declines or holds transactions without human review, while Logistic Regression's high-recall profile is better suited as a wide first-pass filter ahead of a more precise second stage.

In short: for this dataset, F1-score (which balances both) slightly favours Random Forest (0.76 vs. 0.44), but the "right" answer depends on whether the deployment context can tolerate Logistic Regression's much higher false-positive rate in exchange for catching more fraud.

10. Scalability: Handling 1 Million Transactions per Hour¶

The current setup (10K transactions, batch-trained scikit-learn models, single-machine inference) does not directly scale to 1M transactions/hour (~278/second) — a production system would need several changes:

  1. Real-time feature computation. velocity_last_24h and similar rolling-window features currently assume the whole dataset is available at once. At production scale, these need a streaming feature store (e.g. Kafka + a low-latency key-value store like Redis) that maintains rolling counts/aggregates per card in near-real-time, rather than recomputing from a static table.

  2. Low-latency inference. Random Forest with 200 trees is still fast per-prediction (microseconds), but at 278 predictions/second sustained, the model should be served via a dedicated model-serving layer (e.g. a REST/gRPC microservice with the model loaded in memory, horizontally scaled behind a load balancer) rather than reloaded per request. Logistic Regression is cheaper still and may be preferred as a first-pass filter to cheaply clear the ~98.5% of obviously-legitimate traffic, reserving the heavier Random Forest (or a review queue) for the minority of transactions the first pass flags as suspicious — a cascade/tiered architecture.

  3. Asynchronous, non-blocking scoring. Fraud scoring should not sit in the critical path of payment authorization for every transaction if it risks adding latency; many production systems score asynchronously or in parallel with authorization and act on high-confidence fraud signals (e.g. instant block) while routing borderline cases to a fast async review.

  4. Retraining and drift monitoring at scale. Fraud patterns evolve as fraudsters adapt; a static model trained once on 10K historical transactions will decay. Production systems need scheduled retraining pipelines, drift detection on feature distributions and prediction confidence, and feedback loops from confirmed fraud/chargeback outcomes to keep the model current.

  5. Class imbalance at scale doesn't disappear. Even at 1M/hour, fraud will likely remain a small minority — the SMOTE + threshold-tuning approach used here still applies, but retraining on a rolling window of recent data (rather than the full historical volume, which would be enormous) becomes a practical necessity.

In short: the modelling approach here is sound and would transfer conceptually, but moving from a notebook to 1M transactions/hour is primarily an infrastructure and systems-engineering problem (streaming features, tiered low-latency serving, async scoring, continuous retraining) layered on top of the same core algorithms, not a fundamentally different modelling problem.

11. Conclusion¶

Fraud detection is a genuinely different problem from typical classification because the metric that matters (catching rare, costly fraud) is exactly the metric standard accuracy hides. This notebook: confirmed the dataset's severe 1.51% imbalance; showed why accuracy alone would let a "do-nothing" model pass as 98.5% accurate; used SMOTE — applied correctly, after the split, to the training data only — to give both models a fair chance to learn the minority class; and compared two models with very different precision/recall trade-offs (Logistic Regression: high recall, low precision; Random Forest: balanced, higher F1 and AUC).

For deployment, the choice between them is really a business decision about the cost of false positives vs. false negatives — not a question with one universally correct answer, which is itself the most important lesson this dataset teaches.
